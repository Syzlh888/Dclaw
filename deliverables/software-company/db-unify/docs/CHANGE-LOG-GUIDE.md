# DClaw 变更记录规范（CHANGE-LOG-GUIDE）

> 目的：让每一次代码改动都能被后来者一眼看懂。约束团队所有成员（含 AI 助手）在提交/发布/合并前必须写变更。

## 1. 何时写入变更

**必须写**的时机（三选一即触发）：

| 场景 | 写入位置 |
|------|----------|
| **代码提交前** | 若本次提交含用户可感知改动，先更新 CHANGELOG 再 `git commit` |
| **PR 合并前** | Reviewer 必须确认 CHANGELOG 已同步，否则打回 |
| **发布前（build/tag）** | 发版脚本会校验 CHANGELOG 顶部版本号与 `package.json` 一致 |

**可以不写**：纯注释调整、`console.log` 清理、typo 修复、格式化。判断标准：**"用户/交付方是否需要知道"**。

## 2. 写什么（改动分类）

每个版本条目下用**五分类小节**组织（按需选用，不必全有）：

| 分类 | 说明 | 示例 |
|------|------|------|
| **新增** | 新功能、新文件、新依赖、新配置项 | 权限点注册表、SM4 加密层 |
| **修改** | 已有功能行为变更（含 UI 微调、性能优化） | LIMIT 追加逻辑改为智能检测 |
| **修复** | Bug 修复 | 分批加载滚动误触发 |
| **删除** | 删除功能/文件/依赖 | 移除废弃的 v0 API |
| **安全** | 与身份认证、加密、权限相关的独立分类 | JWT 密钥轮换、密码算法升级 |

## 3. 版本条目模板

在 `CHANGELOG.md` **顶部** `# Changelog` 之下、上一版本之前，插入：

```markdown
## [<版本号>] - YYYY-MM-DD

### 新增 / 修改 / 修复 / 删除 / 安全

- **特性名称（简短，可含 emoji）**：一句话概括价值
  - 子项细节 1（技术要点、参数、路径）
  - 子项细节 2

### 修改文件

| 文件 | 改动 |
|------|------|
| `path/to/file.mjs` | 一句话描述 |

### 新增文件

| 文件 | 作用 |
|------|------|
| `path/to/new.mjs` | 一句话描述 |

### 技术细节 (选)

深度实现说明，供后续维护者/审查者查阅。

### 兼容性 (选)

- 是否保留对旧数据/旧格式的兼容？
- 用户/客户端是否需要升级？

### 下一阶段 (选)

后续计划做的事，方便交接。
```

**写作要点**：

- 一级列表描述"做了什么"，二级列表描述"怎么做的"
- 文件路径用反引号包裹
- 数字要具体（"64 个权限点"胜过"若干权限点"）
- 敏感/破坏性改动加 ⚠ 或专门放到 **安全** 分类

## 4. 版本号规则

遵循 [SemVer 2.0](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH`

| 段位 | 何时递增 | 举例 |
|------|----------|------|
| **MAJOR** | 不兼容的 API 变更、数据格式破坏 | `1.x.x` → `2.0.0` |
| **MINOR** | 向下兼容的新功能 | `1.2.x` → `1.3.0` |
| **PATCH** | 向下兼容的 bug 修复 | `1.2.3` → `1.2.4` |

**预发布标签**（正式发布前的迭代）：

```
1.3.0-alpha.1   ← 内部开发中，接口/数据结构可能再变
1.3.0-alpha.2
1.3.0-beta.1    ← 功能齐全，进入内测
1.3.0-rc.1      ← 发布候选，仅修 bug
1.3.0           ← 正式发布
```

**规则**：

- 大改造阶段用 `alpha` 系列滚动更新（如 v1.3 权限体系改造分 7 阶段，每阶段递增 alpha 号）
- 阶段全部完成、进入 QA 测试改用 `beta`
- 客户 UAT 通过改用 `rc`
- 全部签收后去掉预发布标签

## 5. 与设计文档的关系

**设计文档**（如 `docs/permission-design.md`）与 **CHANGELOG** 承担不同职责：

| 维度 | 设计文档 | CHANGELOG |
|------|----------|-----------|
| 视角 | 静态、当前是什么 | 动态、这次改了什么 |
| 更新频率 | 涉及本模块改动时更新 | 每次可感知改动都写 |
| 读者 | 新加入的开发/交付/招标响应 | Reviewer / 客户版本对齐 / bug 追溯 |
| 长度 | 长（数百行） | 短（每版几十行） |

**同步规则**：若改动涉及权限模型/数据模型/协议格式，**先更新设计文档**再写 CHANGELOG，CHANGELOG 里注明 "详见 docs/xxx.md"。

## 6. 发布流程

标准发版顺序（不可颠倒）：

```
1. 完成代码 + 测试通过
2. 更新 docs/*.md（若涉及设计变更）
3. 更新 CHANGELOG.md（顶部插入新版本条目）
4. 更新 package.json version 字段
5. git commit -m "chore(release): v1.3.0-alpha.1"
6. npm run build（打包 / 构建交付物）
7. git tag v1.3.0-alpha.1
8. git push --tags
```

**Pre-commit 建议**：本地钩子检查 `CHANGELOG.md` 是否包含 `package.json` 里的 version（可选，团队协作时加）。

## 7. 反例（不要这样写）

❌ **太模糊**：
```
### 修改
- 优化了权限逻辑
```

✅ **改成**：
```
### 修改
- **权限计算缓存化**：`getUserPermissions` 增加 5 分钟内存缓存，避免每请求查库
  - 新增 `invalidateUserCache(userId)` 供角色变更时主动失效
```

---

❌ **没写文件表**（Reviewer 只能靠 diff 找）：
```
### 新增
- 加了国密支持
```

✅ **改成**：见 v1.3.0-alpha.1 条目，每个新文件一行说明作用。

---

❌ **版本号跳跃**（`1.1.14` → 直接 `1.5.0` 又没解释）：改动大要么走 MAJOR 升级并写迁移说明，要么按阶段用 alpha 号递增。

---

**执行**：本规范自 v1.3.0-alpha.1 起生效。任何 PR 缺失 CHANGELOG 一律打回。
